# Brief – patient login with hospital registration number + PIN (founder, Mon 12 Oct 00:20 IST)

**Why:** the founder's wider vision – SpiroBuddy is for every hospital and clinic; each patient's medicines are saved under their hospital registration number and the patient logs in with it. A registration number alone is printed on every slip, so it is paired with a short PIN.
**Build first in wave 2** (founder: "build the registration number + PIN login first"). One builder (Sonnet is fine) + one checker. Follow the COMMON rules in `docs/rebuild/wave1_workflow.js`.

## What exists already
- `patients.mrn` (text) exists in SQLite (`backend/app/store.py`) and `supabase/schema_v2.sql` → use it as the **registration number**. Show it as "Hospital registration number".
- Patient sessions: `POST /api/me/session` in `backend/app/routes_auth.py` (link token or demo id) sets the `sb_patient` cookie for `authz.PATIENT_SESSION_DAYS`. Reuse its session-creating helper.
- `argon2-cffi` is installed (slow hash for a low-entropy PIN). `backend/app/ratelimit.py` for limits. `audit.write` for every write.

## Build
1. **Schema (additive, both stores):** `patients.pin_hash text`, `patients.pin_failed int default 0`, `patients.pin_locked_until timestamptz`, and a unique index on `(hospital_id, lower(mrn))` where mrn is not null. Add to `supabase/schema_v2.sql` with `add column if not exists` (re-running stays safe) and to the SQLite migrations in `store.py`. **The founder must paste `schema_v2.sql` into Supabase again** – tell them; until then the feature must fail gracefully (a "not set up yet" message, no crash) and everything else must keep working.
2. **Registration numbers:** a patient without `mrn` gets one generated on creation and in the seed: `<hospital prefix>-<6 digits>` (prefix from hospital settings `reg_prefix`, default from the hospital name's initials, e.g. `DGH-000001`). Staff may type the hospital's own number instead (clinics without a system just use the generated one).
3. **PIN:** 6 digits, generated by the server (never chosen by staff), stored only as an argon2 hash, **shown once** to staff. Staff route `POST /api/patients/{pid}/pin` (action `patient.edit`; other hospital → 404 via the middleware) → `{registration_no, pin}` once; audited (never log the PIN).
4. **Login:** `POST /api/me/login {registration_no, pin}` (public path – add to `PUBLIC_PATHS` in `main.py`): trims, ignores case and spaces in the number; on success creates the same patient session as `/api/me/session`. Wrong PIN → one plain message ("That number and PIN don't match. Please check the slip or ask the hospital."), never saying which part was wrong. **5 wrong PINs → that patient is locked for 15 minutes**, plus a per-IP limit (20 / 15 min). Audited (`auth.patient_login`, success and failure, no PIN).
5. **Pages:**
   - `web/patient-login.html`: elderly-first (≥ 20 px text, 64–72 px targets, numeric keyboard `inputmode="numeric"`), English + Hindi at least (ta/ml if quick), two fields + one big button, then go to `/app.html`. In DEMO_MODE show Ravi's demo number and PIN in a dashed "Demo" box (like the staff demo buttons on `login.html`).
   - Staff side, on Ravi's page `web/patient.html` (used in the video – change nothing else): a small "Patient login" card with the registration number and a **"Make a new PIN"** button → shows the PIN once + a printable slip (hospital name, patient name, registration number, PIN, the address `/patient-login.html`, and a QR to it via qrcodejs 1.0.0). Put the logic in a new `web/js/patient-login-card.js`.
   - Links: `login.html` gets "Patient? Log in with your hospital number" → `/patient-login.html`; the landing page hero gets the same link; `meds.html` and `app.html` with no session and no `id`/`t` → a link to it.
6. **Seed:** Ravi (patient 1) gets `mrn` `DGH-000001` and a fixed demo PIN (e.g. `246810`) **only in DEMO_MODE**, recreated on demo reset; other demo patients get numbers too.
7. **Registry:** new key `auth.patient_regno` ("Patient logs in with hospital number + PIN") in `backend/app/features.py`, `in_development` until it works, then `live`. Never say a PIN makes it "secure" or "safe"; say what it does.
8. **Tests** (`tests/test_patient_login.py`): login ok → own data only; wrong PIN message; lockout after 5 and unlock after 15 min (freeze time); PIN never stored in plain text (scan the row) and never in the audit detail; new PIN invalidates the old; staff of the other hospital → 404 on `/pin`; a nurse without `patient.edit` → 403; registration number match ignores case and spaces; missing v2 columns → graceful message; demo PIN only in DEMO_MODE. Run with `tests/test_auth.py`, `tests/test_platform.py`, `tests/test_isolation.py`, `tests/test_meds.py`.
9. Browser check `/patient-login.html` and Ravi's page at 375 + 1440 px, light + dark, real clicks: make a PIN → log in with it → My medicines.
